# Release Process

The main repository coordinates releases and compatibility notes. Core and CLI version and release independently: core is released first when its API changes, and CLI declares its compatible core range. The CLI-owned GitHub adapter ships with the CLI and has no separate release. A release requires independent CI, stable JSON/report contracts, changelog entries, security review, fixture review, and the project release checklist. No remote publication is performed by local development without explicit authorization.

The intended support matrix is Ubuntu, Windows, and macOS on Node 20, 22, and 24. Repository workflows define that matrix, but this audit turn directly executed local verification only on Windows/Node 24; the other matrix cells are not locally verified here. Core is released first; CLI then consumes the exact compatible Core version. The CLI package must be installable from its tarball without a sibling source checkout. Until publication, use a local tarball simulation; never claim registry availability before a real release. Main cross-package tests use built Core/CLI artifacts and remain separate from their implementation.

Before a release candidate can be called externally ready, require the checks in `RELEASE_CHECKLIST.md`, including clean isolated installation of both tarballs, published-package simulation, schema validation, fixture corpus review, and a contributor walkthrough. `npm pack --dry-run` proves package file selection only; it does not prove independent installation or runtime compatibility. No package publication, release creation, merge, or branch-protection change is authorized by this process.
