# Testing Strategy

Core owns deterministic unit tests and rule fixtures. CLI owns filesystem, output, GitHub transport, and failure-mode integration tests. Phase 2 covers help/version, valid JSON audit, strict failure exits, Markdown issue loading, invalid input, and URL parsing. Phase 3 covers nested workflows, lockfiles, tests, issue templates, source/dependency/build-directory exclusion, deterministic inventory ordering, and oversized-file exclusion. Phase 4 covers complete, incomplete, unknown, and not-applicable setup evidence. Phase 5 covers test commands, reproduction guidance, CI workflows, expected results, and regression behavior. Phase 6 covers contribution workflow, pull-request guidance, review expectations, support paths, and SECURITY.md behavior. Phase 7 covers vague and complete local Markdown issues, strict issue exits, and all six issue-readiness dimensions. Phase 8 covers weighted category scoring, score breakdowns, unknown handling, stable report schema, and recommendation ordering. The main repository owns cross-repository fixtures and compatibility checks. Cross-repository tests validate public contracts without making core depend on adapters. Every rule gets pass/fail/unknown and false-positive cases.
## Phase 11 fixture and contract testing

The main repository owns representative repository, issue, and mocked GitHub API fixtures in `fixtures/`. Its dependency-free `tests/contract.test.mjs` imports the built Core and CLI packages to verify that the public evidence, finding, score, report, and adapter contracts remain aligned across repository boundaries. The suite covers excellent, poor, missing, and contradictory evidence; complete and vague issues; deterministic repeated reports; CLI/Core score parity; source-blob exclusion; and offline API-adapter normalization.

See [FIXTURE_CATALOG.md](FIXTURE_CATALOG.md) for scenario intent, expected outcomes, and the recorded false-positive/false-negative review.
