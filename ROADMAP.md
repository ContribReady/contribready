# Executable Roadmap

## Phase 0 — Workspace + Repository Decomposition + Documentation Foundation — complete

Determine repository boundaries from product requirements, create the main repository and only justified supporting repositories, establish project source-of-truth documents, and record the competitive landscape. Exit when the workspace has no parent `.git`, the main/core/CLI repositories have their own `.git`, boundaries are documented, and no unjustified GitHub repository exists.

## Phase 1 — Core Domain Model + Architecture — complete

Purpose: freeze contracts for evidence, rules, findings, reports, and issue analysis. Problem solved: later adapters must share one stable, explainable model. Prerequisite: Phase 0. Tasks: define typed evidence, issue, rule, finding, report, and score contracts; define versioned metadata; add registry shape; add deterministic setup/testing/contribution/security seed rules; add tests. Repositories: core plus project docs. Expected files: `core/src/index.ts`, `core/src/rules.ts`, `core/test/`, `docs/ARCHITECTURE.md`, `docs/SCORING.md`, `docs/RULE_CATALOG.md`. Security: no filesystem, network, token, or target-code execution dependency. Acceptance: identical normalized inputs produce identical findings and score; every finding has rule metadata, evidence, and recommendation; core imports no CLI/GitHub code. Exit: typecheck/build and deterministic tests pass, public contracts are documented, and Phase 2 is unblocked.

## Phase 2 — CLI Foundation — complete

Purpose: provide a usable, safe command surface over the core engine. Problem solved: users need a predictable way to invoke ContribReady without shell execution or hidden network behavior. Prerequisites: Phase 1 core contracts. Implemented: command parsing for `audit` and `issue`; `--help`, `--version`, `--format text|json`, and `--strict`; bounded local reads; regular-file/directory validation; repository evidence loading for the Phase 2 conventional files; Markdown issue title/body loading; human and JSON reports; structured errors; exit codes; and CLI-owned GitHub URL adapter compatibility. Affects: main documentation, CLI implementation/tests, and core public export.

Expected files: `contribready-cli/src/index.ts`, `args.ts`, `errors.ts`, `input.ts`, `output.ts`, `node-shims.d.ts`, `test/cli.test.mjs`, and project CLI documentation. Security: no target scripts, package installation, tests, network requests, shell evaluation, or unbounded file reads. Acceptance: help/version work; valid audit and issue inputs produce stable text/JSON; malformed options and paths return code 2; strict failed audits return code 1; output contains no stack traces; identical inputs produce identical output; and CLI consumes core rules rather than duplicating scoring. Exit criteria: core and CLI typecheck, core tests pass, all CLI tests pass, docs/state/changelogs are updated. Artifacts: CLI foundation source and six passing CLI tests. Next: Phase 3 — Repository Evidence Engine.

## Phase 3 — Repository Evidence Engine — complete

Purpose: turn a local repository into bounded, normalized contributor evidence. Problem solved: rules need consistent evidence across nested workflows, lockfiles, test directories, templates, policies, and documentation without reading arbitrary source or executing repository content. Prerequisites: Phase 2. Implemented: pure core path classification and sorted evidence indexing; CLI recursive discovery; relative-path normalization; contributor-relevant categories for README/documentation, manifests, lockfiles, workflows, tests, templates, and policies; skipped-directory policy; file/depth/count/total-byte limits; oversized and symlink exclusion; evidence inventory and discovery metadata in JSON reports; and deterministic core/CLI tests. Repositories: main docs, core evidence contracts, CLI filesystem adapter/tests. Security: no execution, package installation, network access, arbitrary source reading, or unbounded traversal. Acceptance: nested evidence is found; source, dependency, build, symlink, and oversized files are excluded; inventory order is stable; core classification has no filesystem dependency; and all affected tests/typechecks pass. Exit criteria: documentation, state, changelogs, and tests are updated. Artifacts: `core/src/evidence.ts`, expanded CLI input discovery, evidence fixtures, and passing tests. Next: Phase 4 — Contributor Setup Readiness Rules.

## Phase 4 — Contributor Setup Readiness Rules — complete

Purpose: evaluate whether a contributor can move from repository discovery to a documented local development setup. Problem solved: the presence of files alone does not prove that runtime, installation, development, or environment prerequisites are understandable. Prerequisites: Phase 3 normalized evidence. Implemented: `CR-SETUP-001` through `CR-SETUP-005` for contributor-guide presence, runtime/toolchain prerequisites, package-manager installation, actionable development setup, and environment configuration; explicit pass/fail/unknown/not-applicable semantics; recommendations and false-positive notes; and Core/CLI fixtures. Repositories: core rules/tests, CLI integration tests, main rule catalog/setup documentation. Security: rules inspect text only; no installation, scripts, tests, secrets, or target code execute. Acceptance: complete setup evidence passes; missing manifest installation and missing setup steps fail when applicable; absent environment requirements are not-applicable; runtime heuristics do not treat a package-manager name alone as a runtime version; and all affected checks pass. Exit criteria: roadmap, state, rule catalog, setup documentation, changelogs, typechecks, and tests are updated. Artifacts: setup rule set and deterministic fixtures. Next: Phase 5 — Testing/Reproduction Readiness Rules.

## Phase 5 — Testing/Reproduction Readiness Rules — complete

Purpose: evaluate whether a contributor can run validation, reproduce a behavior, understand CI, and recognize a successful result. Problem solved: a test command alone does not make a repository reproducible or explain what success means. Prerequisites: Phase 4 setup rules and Phase 3 evidence inventory. Implemented: `CR-TEST-001` through `CR-TEST-004` for test-command discoverability, reproduction guidance, CI discoverability, and test expectations; explicit pass/fail/unknown/not-applicable semantics; recommendations and false-positive notes; and Core/CLI fixtures. Repositories: core rules/tests, CLI integration tests, main testing documentation/catalog. Security: rules inspect static text and workflow paths only; no workflow, test, package script, or target code executes. Acceptance: complete testing evidence passes; a command without reproduction/expectation guidance remains visibly incomplete; CI workflow evidence is recognized; missing CI remains unknown rather than an unsupported failure; and all affected checks pass. Exit criteria: roadmap, state, catalog, testing documentation, changelogs, typechecks, and tests are updated. Artifacts: testing/reproduction rule set and deterministic fixtures. Next: Phase 6 — Contribution Documentation Rules.

## Phase 6 — Contribution Documentation Rules — complete

Purpose: evaluate whether an outsider can understand how to contribute, submit a pull request, work through review, and ask for help safely. Problem solved: the existence of CONTRIBUTING.md alone does not make a contribution path actionable. Prerequisites: Phase 5 evidence and testing rules. Implemented: `CR-CONTRIB-001` through `CR-CONTRIB-004` for contribution-guide presence, pull-request workflow, review expectations, and support/contact paths; retained `CR-SECURITY-001` as the vulnerability-reporting check; added explicit pass/fail/unknown/not-applicable semantics; and added Core/CLI fixtures. Repositories: core rules/tests, CLI integration tests, main contributor/rule documentation. Security: rules inspect static text and policy-file presence only; they do not contact maintainers, submit changes, or validate that a channel is active. Acceptance: complete workflow/review/support evidence passes; a bare CONTRIBUTING.md fails missing PR/review guidance; support remains distinct from vulnerability reporting; and all affected checks pass. Exit criteria: roadmap, state, catalog, contribution documentation, changelogs, typechecks, and tests are updated. Artifacts: contribution-readiness rule set and deterministic fixtures. Next: Phase 7 — Issue Readiness Engine.

## Phase 7 — Issue Readiness Engine — complete

Purpose: determine whether an individual local Markdown issue gives an outside contributor enough information to begin and validate work. Problem solved: issue labels and prose alone do not establish context, reproduction, scope, acceptance, or completion criteria. Prerequisites: Phase 6 contribution rules and Phase 3 bounded evidence/input handling. Implemented: local Markdown title/body normalization; six deterministic issue rules for concrete problem/goal, reproduction evidence, expected/observed behavior, technical scope, acceptance criteria, and definition of done/validation; issue-specific human/JSON reports; strict issue exit behavior; and complete/vague issue fixtures. Repositories: core issue rules/tests, CLI issue integration/tests, main issue-readiness documentation. Security: Markdown is inert text; no issue instructions, commands, URLs, or code blocks execute; local issue reads remain bounded. Acceptance: a complete issue passes all six rules; a vague issue produces actionable failures; repository audits do not include issue-only findings; issue `--strict` returns code 1 on failures; and all affected checks pass. Exit criteria: roadmap, state, catalog, issue documentation, changelogs, typechecks, and tests are updated. Artifacts: local issue readiness engine and deterministic fixtures. Next: Phase 8 — Deterministic Scoring + Recommendations.

## Phase 8 — Deterministic Scoring + Recommendations — complete

Purpose: make every readiness score weighted, versioned, explainable, and actionable. Problem solved: an unqualified percentage can hide unknown evidence and provide no order for the next fixes. Prerequisites: Phases 1–7 rule metadata and reports. Implemented: scoring version `1`; setup/testing/contribution/security category weights; issue-specific weighting; explicit pass/fail/unknown/not-applicable handling; category score breakdowns; evaluated/unknown/not-applicable counts; stable report recommendations; deterministic priority ordering; and JSON schema documentation. Repositories: core scoring/report contracts and tests, CLI rendering/integration tests, main scoring/schema documentation. Security: scoring reads normalized findings only and cannot execute or contact target repositories. Acceptance: unknown findings do not earn points; not-applicable findings do not lower scores; category weights sum to the documented maximum; complete issues score independently from repository categories; recommendations place failures before unknowns with stable tie-breakers; and identical findings produce identical reports. Exit criteria: roadmap, state, scoring/schema docs, changelogs, typechecks, and tests are updated. Artifacts: versioned scoring contract and recommendation engine. Next: Phase 9 — GitHub Integration.

## Phase 9 — GitHub Integration — complete

Purpose: allow explicit GitHub URLs to be analyzed without changing the safe local-first default. Problem solved: users need to analyze public or authenticated GitHub issues/repositories while preserving normalized Core contracts and bounded reads. Prerequisites: Phase 8 reports and Phase 2/3 CLI input boundaries. Implemented: canonical HTTPS repository/issue URL parsing; asynchronous opt-in REST retrieval; issue title/body normalization; bounded repository tree/blob retrieval limited to contributor-relevant evidence; optional `GITHUB_TOKEN` authentication; ten-second request timeout; stable authentication, private/unavailable, rate-limit, malformed-response, and network errors; and mocked transport tests. Repositories: CLI adapter/tests and main architecture/requirements documentation. Security: local paths never trigger network requests; tokens are sent only as authorization headers and never included in reports/errors; remote Markdown remains inert; repository evidence remains bounded and classified. Acceptance: canonical URLs retrieve normalized evidence; pull requests are not treated as issues; private/unavailable and rate-limited responses are stable; repeated mocked inputs are deterministic; and all affected checks pass. Exit criteria: roadmap, state, architecture, requirements, changelogs, CLI docs, typechecks, and tests are updated. Artifacts: `cli/src/github/index.ts`, asynchronous CLI entry path, and transport fixtures. GitHub remains CLI-owned because no independent reuse/release/ownership boundary is justified. Next: Phase 10 — Security + Abuse Handling.

## Phase 10 — Security + Abuse Handling — complete

Purpose: make local and remote analysis resilient to hostile paths, URLs, Markdown, API responses, credentials, control characters, and resource pressure. Problem solved: static analysis is only safe when untrusted content cannot execute, escape boundaries, disclose secrets, corrupt terminal output, or consume unbounded resources. Prerequisites: Phase 9 GitHub adapter and all local evidence limits. Implemented: documented threat model; bounded local and remote content checks; oversized issue/JSON/credential rejection; fixed-host HTTPS API requests with redirects refused; terminal control-character sanitization; stable error redaction; and abuse-focused tests for paths, tokens, output, private resources, rate limits, timeouts, and oversized input. Repositories: CLI hardening/tests and main security documentation. Security: no target code, scripts, workflows, Markdown instructions, or package installation execute; local paths remain network-free; tokens are header-only and never reported; remote content is classified and bounded. Acceptance: threat model identifies controls and residual risks; terminal output cannot inject ANSI/control sequences; remote and local limits are tested; GitHub errors do not disclose tokens; and all affected checks pass. Exit criteria: threat model, security docs, roadmap, state, changelogs, typechecks, and tests are updated. Artifacts: `docs/SECURITY_THREAT_MODEL.md`, hardened CLI adapter/output, and abuse-case tests. Next: Phase 11 — Fixture Repositories + Comprehensive Testing.

## Phase 11 — Fixture Repositories + Comprehensive Testing — complete

Purpose: validate product behavior across representative repository and issue states, API responses, and the independent Core/CLI boundaries. Problem solved: package-local unit tests can pass while shared contracts, fixture assumptions, or adapter normalization drift. Prerequisites: Phase 10 security controls and stable Core/CLI report contracts. Implemented: excellent, poor, missing, and contradictory repository fixtures; complete and vague issue fixtures; static GitHub metadata/tree/blob/issue API fixtures; a dependency-free main-repository contract harness; CLI/Core score and report parity checks; deterministic repeated-report checks; source-blob exclusion checks; and an explicit false-positive/false-negative review. Repositories: main fixture corpus/harness plus Core/CLI packages consumed as built artifacts. Security: tests are offline, use no target execution, and treat contradictory evidence as a documented rule gap rather than silently resolving it. Acceptance: fixture outcomes are explicit; complete/vague issues separate cleanly; mocked GitHub data normalizes through the adapter; Core and CLI agree on report contracts; and all affected checks pass. Exit criteria: fixture catalog, testing docs, roadmap, state, changelogs, typechecks, package tests, and cross-package tests are updated. Artifacts: `fixtures/`, `tests/contract.test.mjs`, `docs/FIXTURE_CATALOG.md`, and main test harness. Next: Phase 12 — CI + Packaging.

## Phase 12 — CI + Packaging — complete

Purpose: make the three repositories independently verifiable, packageable, and supportable across the target platforms. Problem solved: local success in one workspace does not establish reproducible builds or release ownership for independent repositories. Prerequisites: Phase 11 fixtures/contracts and stable package boundaries. Implemented: independent GitHub Actions workflows for main/Core/CLI; Node 20/22/24 and Ubuntu/Windows/macOS matrices; package lockfiles; `lint`, `typecheck`, `build`, `test`, `pack:check`, and `verify` scripts; npm package metadata; compatibility matrix; installation smoke checks; and core-before-CLI release ordering. Repositories: all three, with main coordinating documentation only. Security: CI runs project-owned commands, never target-repository code; packaging uses dry-run validation; no publication, remote, or credential action is implicit. Acceptance: each repository has an independent CI path; package artifacts can be dry-run validated; platform/runtime targets are documented; the CLI/Core dependency direction and release order are explicit; and all affected checks pass. Exit criteria: workflows, lockfiles, scripts, compatibility/release docs, roadmap, state, changelogs, and verification runs are updated. Artifacts: three CI workflows, package metadata/locks, `docs/COMPATIBILITY.md`, and independent verify scripts. Next: Phase 13 — v0.1 Product Readiness.

Next: Phase 14 — External Contributor Readiness.

## Phase 14 — External Contributor Readiness — complete

Purpose: ensure an outside contributor can choose the correct repository, set it up, understand the workflow, get support safely, and begin a well-scoped future task. Problem solved: a technically complete product can still be difficult to enter when repository ownership, contribution guidance, support paths, and issue planning are implicit. Prerequisites: Phase 13 release-candidate audit and independent Core/CLI packaging. Implemented: repository-specific contributor workflows for main/Core/CLI; support and security policy documents; setup, verification, branch, pull-request, review, and ownership guidance; three complete local future issue drafts; strict issue-readiness validation of every draft; independent audits of all three repositories; and `EXTERNAL_CONTRIBUTOR_AUDIT.md`. Repositories: all three plus main project coordination. Security: no remote issues or repository changes were created; support guidance excludes secrets; issue drafts are inert Markdown; audits remain static. The policies did not establish that GitHub's private reporting route was enabled; the 2026-10-09 audit confirmed it is disabled. Acceptance: each repository independently scores 100% under the then-current filename/keyword rules; this is not proof that external channels are active. Exit criteria: contributor/support docs, issue drafts, external audit, roadmap, state, README, changelogs, and verification results are updated. Artifacts: repository-specific `CONTRIBUTING.md`/`SUPPORT.md`, `issues/`, and `docs/EXTERNAL_CONTRIBUTOR_AUDIT.md`. Next: Phase 15 — v1 Expansion.

## Phase 15 — v1 Expansion — complete

Purpose: deliver the first bounded additive v1 capabilities without weakening static-first safety or changing the Core/CLI ownership model. Problem solved: CI consumers need interoperable findings, contributors use more ecosystems than the initial manifest set, and GitHub issue context benefits from safe metadata. Prerequisites: Phase 14 external contributor audit, Phase 15 issue drafts, stable report schema, and security threat model. Implemented: opt-in SARIF 2.1.0 projection with stable rule IDs/levels/locations; pure static evidence classification and installation recognition for Deno, Bun, uv/PDM, SBT/Gradle, Docker, Nix, and additional version/toolchain files; additive GitHub issue metadata normalization for state, lock status, comment count, author association, and sorted labels; regression/fixture tests; SARIF and ecosystem documentation; and a security-frozen optional isolated-execution design that is not implemented. Repositories: Core ecosystem contracts/tests, CLI SARIF/GitHub adapter/tests, and main v1 documentation. Security: SARIF does not execute targets; ecosystem detection is text/path-only; remote metadata is bounded and inert; dynamic execution remains prohibited until separately approved. Acceptance: SARIF output is valid and deterministic; text/JSON contracts remain unchanged; new ecosystem evidence is classified without execution; GitHub metadata is additive and safe; all tests/typechecks/package checks pass; and isolated execution has explicit non-goals/prerequisites. Exit criteria: code, tests, v1 docs, design boundary, roadmap, state, and changelogs are updated. Artifacts: `docs/SARIF.md`, `docs/ISOLATED_EXECUTION_DESIGN.md`, SARIF renderer, ecosystem classifier expansion, and GitHub metadata contract. Next: Phase 16+ — Long-term Development.
